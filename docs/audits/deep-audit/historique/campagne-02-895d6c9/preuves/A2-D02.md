# A2-D02 — une modification AppleScript ne déclenchait pas le rendu ni le suivi des changements

Campagne 02, défaut confirmé dans le contrat natif de scripting Cocoa. Correction vérifiée sur les scénarios ciblés ; gates finales encore ouvertes au moment de cette note. Cette preuve ne coche ni `MPDocument.m` ni `MacDown.sdef` dans l'inventaire central.

## Contrat et scénario reproductible

`MacDown/Resources/MacDown.sdef` déclare la classe `document` (`docu`) implémentée par `MPDocument`. La propriété modifiable `text` (`text`) correspond à la clé Cocoa `markdown` ; la propriété en lecture seule `html` (`rndd`) correspond à `html`. Il n'existe pas de commande `exportHTML` dans cette terminologie.

Le parcours réel est : propriété Apple Event `text` → registre `NSScriptSuiteRegistry` et `NSPropertySpecifier` → `MPDocument.setMarkdown:` → vrai `MPEditorView` chargé par le nib → notification de changement → consommateur `editorTextDidChange:` → rendu différé `MPRenderer` → propriété native `html`, puis sauvegarde `NSDocument` du contenu UTF-8. Le setter doit conserver le texte littéral, publier une notification pour un changement réel, permettre le rendu naturel hors mode manuel et conserver un suivi cohérent des changements et de l'annulation.

La fixture crée un fichier UUID sous `NSTemporaryDirectory()`, charge `# Before\n` dans un vrai document et attend que le chargement différé du nib ait effectivement publié cette source. Elle établit le rendu initial puis envoie un véritable Apple Event `core/setd` à son propre processus, sur le thread principal, avec une propriété résolue par la terminologie du bundle. Le nouveau texte contient `# After`, des délimiteurs littéraux et des caractères Unicode. Aucun parse explicite n'est appelé après cette mutation. Le test lit ensuite `text` et `html` par Apple Events, observe la notification, contrôle l'état modifié et sauvegarde réellement le fichier temporaire.

## Rouge natif et cause

`/tmp/macdown-campaign02-scripting-red3.log` : deux tests exécutés, cinq assertions en échec dans le scénario d'édition ; `TEST FAILED`. Le test de mapping natif passe. Après le `setd`, le nouveau texte est bien stocké, mais la notification vaut **0**, le rendu reste celui de **Before** après cinq secondes et le document reste propre. La sauvegarde explicitement forcée conserve le nouveau contenu : le défaut porte sur la publication du changement et ses consommateurs, pas sur le décodage Apple Event ou la sérialisation UTF-8.

Le setter ne faisait qu'affecter `editor.string`. `MPEditorView.setString:` appelle sa superclass et programme la géométrie ; il ne publie pas `didChangeText`. `editorTextDidChange:` ne peut donc programmer le rendu et le suivi normal d'édition n'est pas assuré. Appeler aveuglément `shouldChangeTextInRange:` serait une correction incorrecte : le delegate du document peut transformer un délimiteur tel que `(` en `()` pour l'édition interactive, alors qu'une propriété de source doit rester littérale.

## Correction et branches préservées

`MPDocument.setMarkdown:` conserve le contrat pré-nib via `loadedString`. Lorsque l'éditeur est chargé, il normalise `nil` en chaîne vide, retourne immédiatement sur une valeur identique, capture le texte précédent et enregistre l'opération inverse dans le vrai `NSUndoManager` lorsque l'enregistrement est actif. Il encadre une nouvelle commande par un groupe explicite, sans ouvrir un autre groupe pendant undo/redo, affecte le texte littéral puis appelle `didChangeText` une seule fois. `loadedString` est effacé lorsque le contenu vivant devient la référence.

`NSDocument` compte les groupes enregistrés et les notifications undo/redo. Le setter n'ajoute donc pas un second `NSChangeDone` à ces opérations ; il l'utilise seulement si le manager est absent ou son enregistrement désactivé. Le mode de rendu manuel reste piloté par `needsHtml`, sans parse forcé dans le setter. Les consommateurs examinés comprennent la notification, le rendu différé, `dataOfType:`, la sauvegarde, le chargement différé, l'undo fourni à l'éditeur, la fermeture et les observateurs/watchers de fichier. Le consommateur de contenu CLI pré-nib conserve son contrat.

## Diagnostic du harnais et isolation

Les essais initiaux sur worker ont montré que les Apple Events dirigés vers soi-même s'exécutent synchroniquement sur le thread d'envoi. Le harnais les envoie donc sur le thread principal ; aucun garde de thread n'a été ajouté à la production. Le chargement du nib programme aussi une opération différée : le harnais attend l'égalité de la source avant d'établir sa baseline.

`/tmp/macdown-campaign02-scripting-diagnostic.log` contient une sous-classe temporaire de fixture avec traces de `updateChangeCount:` et notifications du vrai undo manager. Cette instrumentation a ensuite été retirée. Avec `groupsByEvent=YES`, le groupe automatique parent reste ouvert dans l'événement XCTest qui envoie l'Apple Event inline : le setter ouvre les niveaux 1 et 2, ne ferme que son niveau 2, et le document reste propre jusqu'à la clôture du parent. La sauvegarde explicite clôt ensuite le niveau 1, produit exactement un `NSChangeDone`, puis remet le compteur propre. Avec des groupes explicites et autosave désactivé, undo produit exactement un `NSChangeUndone`, redo un `NSChangeRedone`, et chaque retour à la baseline est propre. Aucun double comptage applicatif n'a été confirmé. Ce diagnostic exploratoire utilisait l'ancienne trace qui consultait aussi `canUndo/canRedo` ; ces getters postent des checkpoints et ne sont pas conservés dans la fixture finale.

La fixture finale utilise le **vrai MPDocument**, sans sous-classe ni substitution de notification. Elle désactive `groupsByEvent` pour exercer les groupes explicites de la commande en l'absence de frontière d'événement `NSApplication` dans l'envoi self inline. Elle désactive aussi l'autosave pendant ces seuls scénarios, pour conserver une baseline de sauvegarde explicite. Les deux valeurs sont mémorisées et restaurées dans `tearDown`. Les assertions métier de dirty, notification, source, rendu, sauvegarde et undo sont conservées ; aucun compteur n'est forcé pendant leur observation. Chaque `finally` nettoie le changement temporaire avec `NSChangeCleared`, ferme le document et le retire du contrôleur avant suppression des fichiers.

Les runs natifs ont été sérialisés par le parent dans son vault privé de préférences et d'Application Support, avec fixture home et updater désactivé. Le parent confirme la restauration du vault et le code de sortie **0** de la session verte. Aucun fichier utilisateur n'est utilisé. Les Apple Events ciblent uniquement le processus test, avec `NeverInteract` et timeout cinq secondes ; le nib et les consommateurs Cocoa/AppKit restent réels. Aucun envoi interapplication externe ni publication n'a été effectué.
